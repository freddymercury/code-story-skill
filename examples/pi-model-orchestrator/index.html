How the Pi Model Orchestrator Routes Work

Chapters
mechanism 1 · execution policy

Why is local execution outside the low/medium/high quality ladder?

Because “easy” and “safe to wait for” are different facts. Treating Ollama as the low tier would accidentally make simple interactive work slow.

The first decision is not model quality. It is execution mode. If a task is explicitly background work and safe for the local model, the orchestrator can choose Ollama immediately. Otherwise it returns auto and lets Pi's normal hosted router decide complexity.

src/routing.ts
if (input.locality === "local-only") return LOCAL_WORKER_MODEL;
if (input.mode === "background" && input.localSafe) return LOCAL_WORKER_MODEL;
return "auto";
Key idea: local is an execution constraint, not the bottom rung of a quality ladder.
mechanism 2 · hosted complexity

How does interactive work become Haiku, DeepSeek, or Sonnet?

Once a task stays on the hosted path, Pi's three-tier router can do the job it is actually designed for: classify complexity.

model-router.json
low    → openrouter/anthropic/claude-haiku-4.5
medium → openrouter/deepseek/deepseek-v4-flash-latest
high   → openrouter/~anthropic/claude-sonnet-latest

The classifier itself is Haiku 4.5. Low-tier work stays fast and inexpensive; medium work goes to DeepSeek; high-tier work goes to the current Sonnet family. OpenRouter is not deciding task complexity here. It sits underneath the chosen hosted model and handles the provider/API path.

Watch out: the latest aliases move. They are useful operationally, but they trade reproducibility for automatic upgrades.
mechanism 3 · agent/model separation

How can the same worker use Ollama without becoming “the Qwen agent”?

The model is selected per invocation. Agent identity describes the job; routing context describes how that job should execute.

src/spawn-worker.ts
const model = selectWorkerModel({
  mode: input.mode,
  locality: input.locality ?? "hosted-ok",
  localSafe: input.localSafe ?? false,
});

return orchestrate({ agent: "worker", task: input.task, model }, ctx as never);

A background symbol-extraction task can use the same worker agent with an explicit Ollama model. An interactive implementation task can use that same worker with model: "auto". That keeps model policy outside the agent definition.

Open item: the current adapter casts the Pi runtime context. The routing idea is executable, but the integration should become type-safe with Pi's concrete context type.
mechanism 4 · hard constraints

What is allowed to override the normal model choice?

Privacy and evidence can override normal routing, but they do so for different reasons.

Locality is a hard eligibility rule. If a task is local-only, hosted models never enter the candidate set. Complexity classification cannot overrule that.

Escalation is evidence-driven. A task should move upward when execution reveals that it was under-classified—not because every cheap answer automatically deserves an expensive second opinion.

policy.md
local-only → remove hosted models first

suggested escalation:
local → medium → high
Open item: escalation is currently policy, not retry code. The repository still needs an executable escalation/fallback layer.
mechanism 5 · measured routing

Why are benchmarks and telemetry part of the router itself?

Because “local is slow,” “Haiku is fast,” and “one local worker is enough” are assumptions until measured on the actual machine and provider path.

The benchmark compares local and hosted low-tier work across repetitive coding tasks, records time-to-first-token, total latency, memory pressure, output quality, and retries, then tests whether concurrency improves aggregate throughput.

benchmarks/README.md + policy.md
measure:
- TTFT / total latency
- tokens / cost
- memory pressure
- correctness
- fallback reason
- chosen tier + provider

The initial 7B model and local concurrency of one are deliberately conservative. They should be replaced by measured policy once real numbers exist.

Open item: telemetry is specified but not emitted by the TypeScript helper yet.

Where the “why” came from

  • pi-orchestration upstream: verified per-call model override and model: "auto".
  • Pi docs: verified built-in OpenRouter support and custom Ollama registration through ~/.pi/agent/models.json.
  • Project policy: execution mode, privacy, escalation, observability, and conservative local concurrency.
  • Still unresolved: typed Pi context integration, executable escalation, telemetry emission, and measured local benchmarks.
