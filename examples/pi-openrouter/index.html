How Pi Chooses the Right Worker Model

design dogfood · Pi + Ollama + OpenRouter

Chapters

Mechanism 1 · responsibility boundary

Why are orchestration and model routing separate decisions?

A child agent and a model are not the same thing. If those ideas get coupled, every role quietly becomes a permanent provider choice.

Pi orchestration answers: what work should be delegated, and which role should own it? Model routing answers a different question: what capability and cost tier should execute this particular task?

That separation is what lets a worker sometimes run locally and sometimes use a frontier model without changing the worker definition.

conceptual contractproposed
spawnAgent({ role: "worker", task, model: "auto" })
                         │
                         └── router decides concrete model
Documented: pi-orchestration supports model: "auto" and can inherit Pi's model registry. pi-model-router independently routes work across low/medium/high tiers.
Mechanism 2 · latency is a separate axis

Why does mundane interactive work bypass the three-tier complexity router?

A tiny task can still feel bad if the human is waiting and the local model is slow.

The original instinct was “mundane goes local.” That is incomplete. Mundane describes reasoning difficulty. It says nothing about whether somebody is waiting synchronously.

So the design needs one small decision before the three-tier router: is this mundane work interactive, or can it run in the background?

execution matrixdesign rule
                     FAST NEEDED       LAG OK
mundane              hosted small      Ollama local
complex              premium hosted    economy hosted
Unresolved: the exact Pi extension point for feeding interactive/background invocation metadata into routing still needs implementation verification.

This is why adding a fake fourth tier to pi-model-router would be the wrong abstraction. The extension actually exposes three tiers. Urgency should be input metadata, not a new complexity level.

Mechanism 3 · three capability tiers

How do low, medium, and high become local, economy, and premium execution?

The tier names should describe capability policy, not permanently name Qwen, DeepSeek, or Claude.

pi-model-router gives us exactly the shape we need: configurable low, medium, and high profiles. The important design choice is to keep model identities outside reusable agent definitions.

router mappingproposed
low    -> Ollama local worker
medium -> economy hosted model via OpenRouter
high   -> premium frontier model via OpenRouter

That means you can replace a local 7B coder, swap the economy provider, or change the premium frontier model without rewriting worker, researcher, or reviewer agents.

Why: model availability, price, and quality change faster than agent responsibilities. The routing configuration should absorb that churn.
Mechanism 4 · two routing layers

What does OpenRouter route if Pi already chose the model class?

“Router” appears twice in this architecture, but the two routers solve different problems.

Pi decides which model class should answer the task. OpenRouter sits underneath hosted routes and decides how that selected hosted model is served.

OpenRouter's documentation explicitly separates model selection from provider selection. Provider failover is automatic by default; model fallback is a separate opt-in mechanism.

Watch out: if Pi and OpenRouter both auto-select models independently, it becomes much harder to understand why a task used a particular model and to tune the system.
Mechanism 5 · capabilities over providers

Why should workers ask for capabilities instead of named models?

The same worker role can receive easy extraction work today and difficult implementation work tomorrow.

The forked skill uses three hints: local-ok, economy, and premium. These are not providers. They are statements about what the task needs.

code-story worker examplesimplemented in this repo
change mapper        -> local-ok
evidence finder      -> local-ok / economy
rationale researcher -> economy / premium
story reviewer       -> premium

The host router translates those hints into concrete models. Where metadata is unsupported, the hints still act as policy guidance for the coordinator.

Unresolved: capability hints may eventually live in task metadata, role metadata, or router rules. The design intentionally leaves that encoding open.
Mechanism 6 · hardware shapes policy

How does an 18 GB M3 Pro change the local-agent policy?

Local inference is useful here, but it should not become a requirement that every difficult task fit on the laptop.

The target machine has 18 GB of unified memory. That makes small local coding models useful for repetitive, background work, but it argues against a design that depends on large local models or many concurrent local workers.

The policy is therefore conservative: one substantial local generation at a time, no 30B+ dependency, and reasoning-heavy work moves to hosted economy or premium routes.

local policyoperational
mundane + background -> local
heavy reasoning       -> hosted
local concurrency     -> conservative
large local model     -> optional, never required
Benchmark before pinning: the exact Ollama model, quantization, context length, and tokens/sec should be measured on the machine before becoming defaults.
